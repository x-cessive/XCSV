# PBO-DRIFT-001 - three addons carry fixes that exist only in the deployed PBO

> **CORRECTED 2026-08-10, after reconciliation.** This receipt originally said
> FIVE. It is three. `a3_travellingTrader` and `exile_abandon` were false
> positives and acting on them would have destroyed working code - see the
> correction section at the end. The direction calls below for the three real
> cases were confirmed independently during reconciliation.

Work ID: `PBO-DRIFT-001`

Owning repos: `Exile` (addon source trees), `XCSV` (the audit tool)

Priority: P1 - repacking any of five addons from source silently reverts a live fix

Gauntlet: G2

Date: 2026-08-10

Verdict: `PASS_FINDING` - the audit was built, run across the whole estate, and
found five real instances. Nothing was changed; reconciling them is separate
work and is deliberately not bundled into the discovery.

## Why this was run

`xcsv_chatter.pbo` was found earlier today to contain an entire network handler
that existed nowhere in its source tree - written straight into the deployed PBO
and never written back. A repack from source, which is the documented and
correct way to change an addon, would have silently deleted it. Nothing would
have conflicted, warned, or failed a checksum; the feature would simply have
stopped existing and the PBO that lost it would verify clean.

The obvious question was whether that had happened anywhere else. It had, five
more times.

## The headline is the wrong headline

The tool reports:

```text
No category (a) findings: every deployed file has a source counterpart.
```

That is true and it is misleading, which is worth recording because it nearly
ended the investigation. Category (a) was defined as a **file** present in the
PBO and absent from source - the exact shape of the `xcsv_chatter` case. But
file-level presence is not the risk. The risk is a **regression on deploy**, and
that happens just as completely when the file exists on both sides and the
deployed copy is the one carrying the fix.

Every finding below is a category (c) "content differs" line that the tool
listed without judging, and the judgement is entirely in the direction of the
difference.

## The five

Direction verified by reading both sides directly rather than trusting the diff
orientation - in each case the SOURCE tree is the stock or unfixed version and
the DEPLOYED PBO carries the change.

### 1. `sovran_zeus.pbo` - the deployed whitelist works, the source one is empty

```text
source:   // "76561198000000000"      (commented out, list is empty)
deployed: "76561198108041726"         // atheistics1 / Mr. Sage
```

Repacking from source produces a Zeus addon that grants the Curator interface to
nobody. The source file even carries the warning:

```sqf
if (SOVRAN_ZEUS_UIDS isEqualTo []) exitWith
{
    diag_log "[SOVRAN_ZEUS] whitelist is empty - nobody will be granted Zeus. Edit SOVRAN_ZEUS_UIDS in fn_zeusInit.sqf and repack.";
};
```

So the failure would announce itself in the RPT - but only to somebody already
reading the RPT and wondering why Zeus stopped working.

### 2. `BigfootsShipwrecks_Server.pbo` - the Tanoa fix is only in the PBO

The deployed `config.sqf` carries a dated XCSV change:

```text
// XCSV 2026-08-03: this was still the stock ALTIS config on a TANOA server.
```

The source tree still holds the stock values it replaced:

```sqf
BS_locations_center = [14912.4,15108.7,0]; // ... on Altis this is in the central bay
BS_locations_distance_max = 13000;
```

Repacking would put Altis coordinates back on a Tanoa server. This is the most
consequential of the five, because the symptom is not an error - it is
shipwrecks quietly spawning in the wrong place, or not at all, on a map whose
centre and extents are different.

### 3. `vehicles.pbo` - spawn counts tuned down, only in the PBO

```text
source:   NumberToSpawn = 100;   /   NumberToSpawn = 15;
deployed: NumberToSpawn = 30;    /   NumberToSpawn = 8;
```

Somebody reduced persistent vehicle spawns by roughly two thirds and the change
lives only in the deployed artifact. A repack would push them back up.

This one deserves attention beyond the reconciliation, because the estate has an
open, repeatedly-refuted performance investigation, and "how many persistent
vehicles does this server actually spawn" is a question that investigation has
had to ask. The answer currently differs depending on which copy is read.

### 4. `a3_travellingTrader.pbo` - map-aware logic only in the PBO

The deployed `travellingtrader.sqf` derives its spawn area from `worldSize` and
branches on `worldName`; the source is the stock version with hand-set distances
and a Chernarus branch. Same shape as the shipwrecks case.

### 5. `exile_abandon.pbo` - refund and delete logic only in the PBO

The deployed `fn_abandonterritory.sqf` looks up `CfgConstruction` refund objects,
adds a codelock back when the object had an access code, and calls
`ExileServer_object_construction_database_delete`. The source version does none
of that. Repacking would drop territory refunds and leave rows behind in the
database.

## What is NOT a finding

Our own two PBOs - `Exile.Tanoa.pbo` and `xcsv_chatter.pbo` - also report as
differing, in the opposite direction: source is ahead because today's XM8 work is
staged and undeployed. That is expected and is the normal state between packing
and deploying.

Nineteen vendor addons matched their source exactly, including the large ones
(`A3XAI` 166 files, `a3_dms` 130, `a3_exile_occupation` 47). Eight PBOs have no
source tree at all and were listed rather than silently skipped - among them
`exile_server_config.pbo`, a single 326 KB `config.cpp` holding every trader,
price and loadout on the server, for which **the deployed PBO is the only copy in
existence**. That is not drift, but it is the same risk in a more advanced state
and is worth its own entry.

## Correction needed in the tool

`pbo-drift-audit.ps1` should not report "no category (a) findings" as a
conclusion when it has listed content differences it has not judged. Either the
summary should refuse to say anything reassuring while category (c) is non-empty,
or - better - the tool should determine direction per file and split category (c)
into "source ahead, expected before a deploy" and "DEPLOYED AHEAD, a repack will
revert this". The second is the one that matters and it is the one a reader will
miss.

## CORRECTION - two of the five were false positives

Reconciliation found that `a3_travellingTrader` and `exile_abandon` are not
local drift at all, and that acting on this receipt as originally written would
have **deleted working code**.

The deployed PBOs for both are **SHA256-identical to the vendors' own
pre-packaged PBOs already committed in this repo** -
`Addons\ExileTravellingTrader\pre-packaged pbo\a3_travellingTrader.pbo` and
`Addons\Exile_Abandon_Territory\Server\exile_abandon.pbo`. Both prepacks entered
with their vendor-import commits and are unmodified, and neither source file has
been touched since import.

So what the audit saw was the **vendor's own source-versus-shipped-binary
drift**, and in both cases **the source is the newer side**. `exile_abandon`
source uses `refundObjects`, re-adds a codelock, and calls
`ExileServer_object_construction_database_delete` - which does exist in
`exile_server.pbo`. The shipped binary predates all of it. Copying deployed over
source, which is what this receipt originally implied, would have removed refund
and database-cleanup logic that works.

Both were left untouched.

Note the inverse, which is a real decision rather than a cleanup: repacking
either of those two **from source is a live behaviour change**. Abandon would
start refunding kits and deleting rows; the travelling trader would lose its
per-map branches.

**The lesson for the tool:** where a vendor ships a pre-packaged PBO and the repo
carries it, compare against THAT before concluding anything about direction. A
deployed file matching the vendor's own binary is not evidence of local work; it
is evidence of the absence of it. That single check would have caught both false
positives, and it belongs in the "teach it direction" work below.

Also corrected: `BigfootsShipwrecks`'s `readme.txt` is **source-ahead**, not
cosmetic - source documents v1.0.2 and the packed copy only v1.0.0. It was left
alone rather than overwritten to make an audit line go green.

## Correction: what `exile_server_config.pbo` actually holds

This receipt and the roadmap entry both claimed it contains "every trader, price
and loadout on the server". That is wrong, and the error mattered because it
overstated the emergency.

It holds `CfgBuildings` (loot spawn positions), `CfgExileLootServer` and
`CfgExileEscapeLootServer` (loot tables), and `CfgSettings` - respect and kill
feed, the bambi spawn loadout, vehicle spawn, weather, time, RCON, and the
scheduled events including base cleanup and abandoned-territory with
`territoryLifeTime = 7`. The traders, prices and purchasable loadouts live in the
MISSION, which is version-controlled.

Still very much worth holding - it is the difference between a rebuildable server
and a guess - but the economy proper was never the thing at risk here. Whether
anything else economy-related is unsourced is a separate question and has not
been checked.

Two traps were found while closing it, both of which would have silently defeated
the backup:

- **The repo's `* text=auto` rule corrupted the stored copy.** `config.cpp` has
  mixed line endings - mostly CRLF with bare LF at the tail - so a naive commit
  and checkout produced a file whose hash no longer matched the live extract. A
  restore from that commit would have yielded something that is not what is
  deployed. Fixed by marking the tree `-text`, verified by repacking from a clean
  checkout and re-diffing.
- **That rule has to live in the ROOT `.gitattributes`.** `pbo.ps1`'s metadata
  exclusion list does not cover `.gitattributes`, so a copy placed inside the
  addon folder packs into the addon as a spurious second entry.
