# XM8-APPS-002 - the Inspector's empty pane was four separate things

Work ID: `XM8-APPS-002`

Owning repos: `Exile` (mission source + server addon source), `XCSV_GUARD`
(doctor, config default)

Priority: P2 - follow-up to the one unverified item in XM8-APPS-001

Gauntlet: G3

Date: 2026-08-10

Verdict: `PASS_PENDING_DEPLOY` - every defect found and fixed at source, GUARD
side proven at runtime; the mission half is packed and staged but not swapped in,
because that needs the server stopped.

## What this was supposed to be

XM8-APPS-001 closed with one item open: *"Player Inspector renders its frame and
GO BACK but its content area was empty. That was observed while slides were
still bleeding over each other, so it is not yet a trustworthy observation -
unverified, not known-broken."*

Looking at it turned up four defects. None of them was the one being looked for.

## 1. The app had never run, and its resting state looks like a fault

`grep XCSV_IN[S]` across every RPT in `E:\arma3server\profiles` returns **zero
lines**. Both the success path and the refusal path in
`fn_inspectorRequest.sqf` end in a `diag_log`, so a single request - authorised
or not - would have left a trace. The app had never been exercised past opening
it.

Which makes the reported symptom exactly what the code does. Player Inspector is
a search box: `XCSV_fnc_inspectorShow` deliberately clears the result list and
the detail pane, then waits for a name. An empty pane is its correct resting
state.

That is still a defect, just not a functional one. Trader Prices in the same
release writes *"Type in the box above to search, then pick a result"* into its
empty pane; the Inspector wrote nothing, so an empty rectangle under a "Player
Inspector" title reads as a broken app - which is precisely how it got reported.
It now renders a hint on open.

It also could not distinguish two different outcomes: a search that matched
nobody left the pane in the same state as a search that was never sent. A "No
match" message now covers that.

## 2. The Enter key raised a script error on every press

```sqf
onKeyDown = "_this select 1 == 28 && {call XCSV_fnc_inspectorRequest}; false"
```

`XCSV_fnc_inspectorRequest` ends in `systemChat`, which returns Nothing. `&&`
wants a Boolean on both sides, so this raised

```text
Error &&: Type Nothing, expected Bool
```

on every Enter. The block runs to completion before `&&` inspects its result, so
the request was still sent - the only symptom was an error popup, and this server
runs `-showScriptErrors`. Rewritten as `if/then`, which does not care what the
block returns, so the handler stays free to end however it likes.

## 3. The response would have been unparseable the first time it fired

`xcsvInspectorLookup` declared

```ini
OUTPUT = 1-STRING,2-STRING,3,4,5,6,7,8,9
```

Columns 7 and 8 are `first_connect_at` and `last_connect_at`, both DATETIME.
`xcsvInspectorTerritories` had the same problem with `last_paid_at` at column 5.

A datetime renders as `2026-08-01 10:06:38` - it contains a space, so untyped
and therefore unquoted it cannot survive being read back as an SQF array. The
row would have arrived malformed, `_rows` would have stayed empty, and the app
would have shown nothing for a player who plainly exists.

This is not inference from first principles. Exile's own `loadTerritory` in the
same file tags `last_paid_at` as `12-STRING` while leaving the numeric columns
bare, so the house rule is already written down in the file being edited. Both
copies of `exile.ini` were patched - `@ExileServer\sql_custom\` and
`@ExileServer\extDB\sql_custom\`, which are kept identical - and each diffed
against its own pre-change backup to confirm **exactly two lines changed** and
nothing else matched the replacement patterns.

Not yet proven at runtime: extDB3 reads `sql_custom` at init, so this takes
effect on the next server start.

## 4. The server addon's source tree was stale

The deployed `xcsv_chatter.pbo` contains `network\fn_inspectorRequest.sqf`
(3,083 bytes), `class inspectorRequest {}` in `config.cpp`, and the
`ExileServer_system_xcsv_network_xcsvInspectRequest` alias in
`bootstrap\fn_postInit.sqf`.

`E:\ExileRepo\LiveSource\server-addons\xcsv_chatter` contained **none of the
three**. The inspector was built on 08-06 and deployed straight into the PBO
without ever being written back to source.

So repacking that addon from source would have silently deleted the server half
of the app, leaving a client that sends a request nothing will ever answer. That
is the same failure mode as the `mission_src` finding an hour earlier, in a
different place, and it is the more dangerous half: a mission rollback is
visible, a missing network handler just times out in silence.

Reconciled by unpacking the deployed PBO and taking the three changes back into
source. Everything else that appeared to differ was CRLF-versus-LF; after
`diff --strip-trailing-cr` the only remaining differences are indentation the
PBO copy had lost and the ordering of four empty class declarations.

## 5. Doctor was pointed at the dead directory too

`doctor.ps1` defaulted:

```powershell
[string]$MissionSrc = 'E:\ArmaTools\mission\Exile.Tanoa',
```

its own literal copy of the path GUARD had been repointed away from an hour
earlier. Three checks read it - `safezone-class`, `hc-slot` and `mission-drift` -
so all three had been quietly reporting on an abandoned 08-05 copy.

`mission-drift` is the one that matters. Catching "source edited, PBO not
rebuilt" is its entire job. It was returning a confident PASS while comparing two
files that had nothing to do with the running server, and it is exactly the check
that should have caught the `mission_src` bug in the first place - blind for the
same reason.

The fix is not to correct the literal. Two literals that must agree will
eventually disagree, and this one failed silently in the direction where
everything passes. `$MissionSrc` is now **derived** from GUARD's own
`mission_src`, with `-MissionSrc` still available as an override for testing
against a candidate tree. If the config cannot be read at all it warns and skips
those three checks rather than guessing: a wrong path is worse than no path,
which is the whole lesson here.

GUARD's compiled-in default in `config.rs` carried the dead path as well, so a
freshly created config could reintroduce it. Repointed.

## Proof

**The check now works.** With the mission source edited and deliberately not yet
repacked:

```text
FAIL  mission-drift  2 source file(s) newer than the deployed PBO
      -> Edits are not live until repacked. Newest: config.cpp
```

Two files, which is exactly what was touched (`config.cpp`,
`xcsv\fn_playerInspector.sqf`). Against the same tree before the fix it read
`PASS  mission-drift  deployed mission PBO is current`. `safezone-class` and
`hc-slot` continue to pass, now against the real tree.

**GUARD**: `cargo test` 267 passed, 0 failed, 3 ignored - unchanged from the
morning's `guard-0.7.1+23`.

**The server path, as far as it can be proven from outside the game**: the
lookup SQL run directly against the live database returns exactly one row, the
operator's account, with all nine columns populated. Its
`uid REGEXP '^7656119[0-9]{10}$'` guard correctly excludes the six `HC*` accounts
that would otherwise match a name fragment - the headless clients register as
accounts named `headlessclient`. The territory query returns empty for that UID,
which is correct: they own no flag, and the app renders the Flags block only when
there is one.

**Mission PBO**: packed from the reconciled source, `358 files, 4,332,678 bytes`,
`checksum OK`, staged at `D:\CAGE\xcsv-runtime\Exile.Tanoa.staging.pbo`.

## Not deployed

The mission changes are inert. `E:\arma3server\mpmissions\Exile.Tanoa.pbo` is
held open by the running server, so the swap needs the stack stopped, and the
`exile.ini` OUTPUT fix needs a server start to be read at all.

The clean path is GUARD's own supervised cycle - STOP, "Repack mission" (safe now
that `mission_src` is correct), START - rather than killing the processes, which
would trip `auto_restart_on_crash` and file a spurious autopsy.

A pre-swap backup of the live PBO was NOT taken, because the swap did not happen;
take one at deploy time.
