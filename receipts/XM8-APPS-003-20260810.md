# XM8-APPS-003 - a full forensic pass over every custom XM8 app

Work ID: `XM8-APPS-003`

Owning repos: `Exile` (mission source + server addon source)

Priority: P1 - one feature was found to have never worked at all

Gauntlet: G3

Date: 2026-08-10

Verdict: `PASS_PENDING_DEPLOY` - all defects fixed at source and reviewed by an
independent model; nothing is deployed, because writing to the live server
directory and stopping/starting the stack are both blocked in this environment.

## Method

Three independent auditors were run in parallel, one per app cluster, each given
the same brief: find defects, prove them, and separate EVIDENCED from INFERRED.
Their findings were then verified by hand before anything was changed - two
proposed patches were rejected on inspection and one was rewritten.

A separate provider (OpenAI `gpt-5.5` via `codex exec`, read-only sandbox) ran
two adversarial critic passes: one over the Player Inspector changes from
XM8-APPS-002, and one over this entire batch checking specifically for syntax
that would break the mission on deploy. Findings that survived checking were
applied; findings that did not are recorded below with the reason.

## The big one: Insurance has never worked

`ExileServer_system_network_dispatchIncomingMessage` derives its handler name
mechanically:

```sqf
_functionName = format ["ExileServer_%1_network_%2", _moduleName, _messageName];
_functionCode = missionNamespace getVariable [_functionName, ""];
if (_functionCode isEqualTo "") then { throw format ["Invalid function call! Called: %1", _functionName]; };
```

The message is declared in `CfgNetworkMessages` as `xcsvPolicyBuyRequest` with
module `system_xcsv`. So the only name the dispatcher will ever look up is
`ExileServer_system_xcsv_network_xcsvPolicyBuyRequest`.

`xcsv_chatter\bootstrap\fn_postInit.sqf` aliased
`ExileServer_system_xcsv_network_policyBuyRequest` - the message name without its
`xcsv` prefix.

Every press of BUY POLICY therefore threw inside the dispatcher, which catches
and logs server-side only. No toast, no error, no refusal reached the player.
The two sibling aliases on the following two lines
(`...xcsvTeleportRequest`, `...xcsvInspectRequest`) have always been correct,
which is what makes this a typo rather than a misunderstanding.

**Evidence it never fired:** across all 20 server RPTs on the box there are zero
occurrences of `bought a policy`, zero `refused:`, zero `Invalid function call`,
and every `loaded N charge(s)` line reads zero. The success path - the
`xcsvPolicyBuy` INSERT, the reload of a non-zero charge count, and the entire
death-payout function - has never executed. The first live purchase will be the
first real test of all of it.

This is the only client-to-server write path in the whole subsystem and it spends
player money, so the surrounding audit mattered as much as the fix.

## Everything else found

### Insurance

- **A failed purchase looked exactly like a successful one.** All feedback was
  delegated to a server toast that could not arrive. The client now compares the
  charge count before and after. The message deliberately does not claim the
  server was silent - a genuine refusal (broke, at max charges) leaves the count
  unchanged too, and the server explains those itself. All the line can honestly
  assert is that nothing changed and nothing was taken. *(That wording was a
  critic finding: my first version said "no response from the server", which
  would have contradicted a refusal message the player could see on screen.)*
- **The rate limit only covered success.** The cooldown was stamped after every
  validation passed, so refusal paths - dead, broke, at max charges - were free
  to repeat immediately, and the 3-second client-side timer that normally hides
  that runs on a machine the player controls. Stamped on attempt now. The
  database was never exposed: every refusal returns before any query, so this is
  a log and CPU fix, not a data one.
- **Headless clients were being swept.** `allPlayers` includes them, so every
  restart spent a database round trip looking up policies for `HC6940` and hung
  an MPKilled handler on something that cannot buy insurance. It also wrote a
  misleading `loaded 0 charge(s) for HC18844` into the very log used to prove the
  feature works. A real Steam UID is 17 characters; an HC's is `HC` + pid.
- **The price was duplicated as a literal** in the button caption
  (`BUY POLICY - 2500`) while the authoritative constant lives in a different PBO
  deployed by a different step. Caption no longer states a number.

The mandated security checklist otherwise passed in full, and this is worth
recording as a positive result: identity is resolved server-side from the
session, the wire carries literally no parameters, affordability is checked
immediately before deduction with nothing suspending in between, money comes off
before the policy is granted, and the money mutation is byte-identical to
Exile's own `payTerritoryProtectionMoneyRequest`.

### Scoreboard

- **Player names were rendered into structured text unescaped.** Structured text
  is XML-ish, so one Steam name containing `&` or `<` corrupts the markup of the
  whole board - for every player who opens it, not just that one. A single row
  poisons the entire control.

  The interesting part is why it was missed. `fn_standing.sqf` had already found
  this exact risk and documented it at length, and escapes correctly. But the
  helper lived *inside* that file, so it read as part of the Standing app rather
  than as something shared, and the scoreboard silently went without. That is the
  same shape as two other defects found the same day - GUARD and doctor each
  holding a literal copy of `mission_src`, and the Inspector's admin list
  existing on both sides of the network. `XCSV_fnc_esc` now lives in
  `xcsv\fn_shared.sqf` with one definition and two callers.

  Ordering matters in the fix: the 18-character truncation runs BEFORE the
  escape, because escaping first would let the cut land inside an entity like
  `&amp;` and emit `&am`, which is just as broken as the character it replaced.

- **"Updated N minutes ago" compared two unrelated clocks.** The publisher
  broadcast its own `diag_tickTime` and the client subtracted that from *its*
  `diag_tickTime`. That value is time since each machine's engine started, so a
  client that had Arma open longer than the server read a large positive age and
  a freshly joined one read a large negative age. The footer was only ever right
  by coincidence. Both sides now use `serverTime`, which reads identically
  everywhere. Both had to change together.

- **`str` on a large score emits scientific notation.** `str 1234567` is
  `"1.23457e+006"`, and a respect leaderboard is precisely where six figures get
  crossed. The mission had already been bitten by this and carries a k/m
  formatter for the XM8 home screen; the scoreboard now uses the same convention
  via `XCSV_fnc_num` so the two screens agree.

### Field Notes

- **The manual understated protection money fivefold.** It said "10 poptabs per
  object". Exile charges `level * perObject * objects`, so a level 5 base with
  100 objects costs 5,000 a cycle, not 1,000 - rising to tenfold at level 10.
  This is in the section headed "DECAY IS THE THING THAT KILLS BASES", and the
  file's own header says "a manual that lies is worse than no manual".

Every other number in the notes was checked against config and is correct:
territory limits and radii, the 5-minute post-charge build block, sell factor,
rekey cost, virtual garage capacities, and the 150 m build ceiling.

### Player Inspector (continuing XM8-APPS-002)

- **It was the only app of six with no `disableSerialization`.** Every sibling
  calls it; this one called it zero times. Added to all six UI-touching
  functions.
- **Numpad Enter did nothing.** The handler accepted DIK 28 only. Now `[28, 156]`.
- **A wildcard in the search box returned the wrong player.** This is a
  correctness guard, not a security one - the fragment was always bound as a
  positional `?` and never concatenated into SQL. But `%` makes `%<fragment>%`
  match every account, and the query is `ORDER BY last_connect_at DESC LIMIT 1`,
  so the app would confidently render *somebody* rather than fail. Stripped on
  both sides, authoritatively on the server.

  Implemented with character codes - `toString ((toArray _x) select { !(_x in
  [37, 95, 92]) })` - rather than string literals, because one of the three
  characters is a backslash and Arma's preprocessor reads a backslash as a line
  continuation. It was also deliberately not done with `regexMatch`, because new
  engine commands have to be cleared through BattlEye's `scripts.txt` before a
  live client may use them, and a filter kick is a far worse outcome than a
  longer loop.
- **Refusals were silent.** The server logged them and answered nothing, so a
  refused admin waited forever on a screen identical to "still loading". It now
  replies with an empty result, which renders as "No match" - deliberately
  identical to a genuine miss, so the reply cannot be used to probe the
  whitelist. The real reason stays in the server log.

### Standing

Audited against the same checklist and found **clean**. Arity matches between
publisher and client, no type traps, division guarded, `min`/`max` precedence
correct and additionally parenthesised, no `select` overrun, escaping present
and correct, control lookup right, UID typed `-STRING` so the comparison works.
Recording the negative result deliberately.

One tuning observation, not a defect: the three standing axes saturate early
(13 kills, 12,500 poptabs, 50 connections), so established players will likely
read 100/100/100 on all three and the app stops discriminating. That is a design
call for the owner, not a bug, and it could not be checked against real data
because MariaDB was stopped during the audit.

## The structural fix: every render function now logs

Until today the only thing any XCSV app ever logged was that its *file had
loaded*. Nothing logged that a render had actually happened.

That is exactly why the Player Inspector could sit visibly broken with nobody
able to say whether its display path had ever run, and why two of the three
auditors had to report "static analysis only, no runtime evidence available" for
the client half of their apps. One `diag_log` per render function makes the
question answerable from the client RPT, permanently and cheaply.

## Critic findings NOT applied, and why

- **Escape-then-truncate ordering.** One auditor proposed escaping before
  truncating. Rejected: that lets the 17-character cut land inside an entity.
  Truncate first, escape last.
- **`regexMatch` for the HC filter and the wildcard strip.** Rejected on the
  client for the BattlEye reason above, and rejected on the server for
  consistency; a length test and a character-code filter do the same job with no
  new engine command.
- **Scoreboard column realignment.** The columns genuinely do not align - the
  header and rows are 1-2 characters adrift and the padding only works in a
  monospace face, which is not guaranteed. The correct fix already exists as dead
  code in that file (`XCSV_fnc_sbCell`, which emits per-column `align=`). It was
  NOT applied here: it is a rewrite of the render loop, the file's own comment
  already concedes the current approach is approximate, and rewriting a render
  path that cannot be looked at before deploying is how the six original defects
  got in. Recorded as roadmap work instead.
