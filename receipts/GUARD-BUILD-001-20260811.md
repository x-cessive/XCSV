# GUARD-BUILD-001 — Steam build alignment gate

**Date:** 2026-08-11
**Repo:** XCSV_GUARD
**Status:** implemented, tested; runtime-verified against the live outage that produced it

## The outage

Nothing could join the server. Not the headless clients, not the operator.

Every ordinary health signal read green:

- `arma3server_x64.exe` up, pid 31416
- UDP 2302 / 2303 / 2304 / 2306 bound
- `Starting mission:` reached, exactly once — no mission restart loop
- `CallExtension loaded: extDB3 … [extDB3 v1033 Windows]`
- `"ExileServer - Connected to database!"`
- `Connected to Steam servers`

No error in the server RPT. No BattlEye rejection. No kick line. Nothing in the
logs described the fault at all.

The evidence was in two version banners, in two different RPT files, that
nothing compares:

| | Version | Exe timestamp | Steam buildid |
|---|---|---|---|
| `arma3server_x64.exe` | 2.20.152984 | 2025/06/24 | 18981937 |
| `arma3_x64.exe` (client / HC) | 2.22.153995 | 2026/08/06 | 24672225 |

Steam auto-updated the retail client on 2026-08-06. The dedicated server is a
SteamCMD install of a different app (233780) and does not update with it, so it
stayed on the 2025 build.

Arma 3 refuses cross-version joins, and refuses them *silently from the
server's side*: a client failing the version handshake never reaches the point
where the server would log a join. The server therefore observes only that
players never arrive.

## Why it got worse on its own

GUARD read "no players" as an unhealthy server and bounced it. Server RPTs at
15:09 → 15:18 → 15:31 are that loop. Each relaunch produced a fresh, equally
unjoinable server, and the restart logs recorded a cause — unhealthy — that was
a symptom of a fault nothing in the restart path could see.

Killing the processes was not enough to stop it: `XCSV_GUARD.exe` (pid 28180)
is the parent of the respawned server and revived it within seconds. The stack
only stayed down once GUARD itself was stopped first.

`fps-watch.ps1` was considered and cleared — it is read-only with respect to
the game and starts and kills nothing.

## The fix

A preflight gate that compares the two Steam build ids before launching,
because both are knowable from disk without starting anything. Each install
records its build in a plain-text Valve ACF manifest:

```
E:\arma3server\steamapps\appmanifest_233780.acf     server
E:\SteamLibrary\steamapps\appmanifest_107410.acf    client
```

New module `src/steambuild.rs`. Three verdicts:

- **Aligned** — start proceeds.
- **Mismatch** — start is refused. A server on the wrong build is unjoinable by
  every client on the network, so launching it can only reproduce the silent
  restart loop this gate exists to prevent.
- **Unknown** — a manifest is missing or unparseable. Warns loudly and **starts
  anyway**. Absence of evidence must not become an outage; a moved Steam
  library is a monitoring gap, not a reason to refuse to run a server that may
  be perfectly healthy.

Two design points worth keeping:

- **No backoff on a blocked start.** `disarm_relaunch()` leaves nothing armed.
  Nothing about a build mismatch changes by waiting, so retrying would rebuild
  the exact every-few-minutes loop that hid the fault. GUARD stops and waits
  for the operator.
- **Never cached across a start attempt.** Both manifests are re-read on every
  launch. A client updating between launches is precisely the event this must
  catch; a stale ALIGNED verdict would wave through an unjoinable server.

The module is read-only: it never runs SteamCMD and never updates anything.
Naming the fault is the job. Applying a multi-gigabyte update is an operator
decision and must not fire from an autostart path while nobody is watching.

## Surfaces

- Preflight gate in `finish_start_server`, ahead of the PBO gate — a build
  mismatch outranks addon integrity because it defeats every client regardless.
- Telegram notification on a blocked start, carrying the remedy.
- Red banner on Overview when mismatched; a dim line when the check is Unknown.
- Integrity tab: `block start on Steam build mismatch` toggle (default on) and
  the current verdict.
- Registered in `state_model` as `steam.build_check`.

## Tests

334 passed, 0 failed, 3 ignored (332 before; 9 new in `steambuild`).

The new tests include the outage reconstructed from the two real manifests —
18981937 vs 24672225 — asserting it is detected and blocks; that `TargetBuildID`
is never read in place of `buildid` (which would report a pending update as
already applied); and that an unreadable manifest is Unknown and never blocks.

Two existing guards failed first and were repaired rather than weakened:

- `relaunch_tests::the_reset_is_on_the_success_path_not_unconditional` —
  `start_server_code()` scans worker.rs through `finish_start_server`, so a bare
  `self.relaunch_at = None;` in the new refusal branch tripped the ordering
  assertion. Moved behind `disarm_relaunch()`, defined outside the scanned span,
  so the literal guard stays literal.
- `state_model::every_guard_app_field_is_classified` — new state must be
  classified. Added `steam.build_check`.

## Still outstanding

The server is still on build 18981937 and remains unjoinable until it is
updated with SteamCMD (app 233780). The gate will refuse to start it until
then, which is the intended behaviour.
