# XM8-APPS-001 - the custom XM8 apps, made to actually work

Work ID: `XM8-APPS-001`

Owning repos: `Exile` (mission source), `E:\ArmaTools` (tooling, unversioned)

Priority: P2 - every custom XM8 app was unusable

Gauntlet: G3

Date: 2026-08-10

Verdict: `PASS_PARTIAL` - five of six apps confirmed rendering in game; Player
Inspector renders its frame but its content is unverified.

## What the operator reported

The XM8 extra-apps page was "all overlayed and glitched", nothing could be
clicked, and every custom app showed the same settings-gear icon.

## What was actually wrong

Six separate defects, stacked. The first one hid the rest, which is why this
took several passes: each fix exposed the next layer.

### 1. Grid geometry

The override forced every button to `2.5*(0.04)` = 0.10 tall when
`RscExileXM8AppButton1x1` declares `5*(0.04)` = 0.20.

`ShortcutPos` and `TextPos` are derived from the CONFIG constants, not from the
runtime size, so a half-height button gets a full-size icon spilling over its
neighbours and a label at y-offset 0.13 - outside a 0.10-tall control, which is
why no custom app ever showed its name. The row pitch was also halved, so every
row overlapped the one above.

### 2. Wrong parent - the reason nothing was clickable

Buttons were created with `_display ctrlCreate`, so they belonged to no slide.
The extra-apps slide is a controls group covering the tablet; it sits over
display-level controls and takes the mouse input they should receive. The
buttons were visible through it and deaf to it - including the STOCK apps, which
is the clue that ruled out anything per-app.

`ExileClient_gui_xm8_slide` resolves a slide by name:

```sqf
controlID = getNumber (configFile >> "CfgXM8" >> <slide> >> "controlID")
```

so the group is fetchable at runtime with no hardcoded id. Buttons are now
created inside it and inherit its coordinates, input handling and hiding.

### 3. No teardown

We overrode `extraApps_onOpen` but not `extraApps_onClose`, so stock cleanup
removed stock's controls and left ours alive on the display - painting over the
home screen and stacking another 26 controls on every open. Both halves now
exist and share one teardown file.

### 4. The slides never existed

The big one. `XM8SlideXcsvScoreboard` and friends were only ever CLASSES in the
mission config. A class is not a control. Nothing in the mission ever created
them, so `displayCtrl 71800` returned null, the slide switch silently did
nothing to a null control, and the app opened as a titled blank page with no GO
BACK.

**Every XCSV app had behaved this way since it shipped.** Nobody noticed because
none of them could be clicked. `onOpen` now creates each app's `resource` slide
if absent, and deliberately leaves it alive - tearing it down would delete the
slide the app is switching into.

### 5. Duplicate and missing registrations

- `XM8SlideXcsvPrices` and `XM8SlideXcsvStanding` both used `idc = 71820`, and
  both wrote to control `71821`. Two apps fighting over the same controls.
  Prices renumbered into its own `7185x` block; `fn_traderPrices.sqf` updated.
- `xcsvPrices` and `xcsvPolicy` had no `CfgXM8` entry at all. Slide switching
  resolves only through that config, so both would have looked up controlID 0.
  Both registered.

### 6. A class that could never instantiate

`RscExileXM8SearchEdit` inherited `RscEdit`. Mission config resolves base classes
from @Exile's config fine - `RscXcsvXM8AppButtonGrid` inherits
`RscExileXM8AppButton` and renders correctly - but it does NOT resolve Arma's own
UI bases, so the class had no `type` and `ctrlCreate` died with

```text
No entry '...description.ext/XM8SlideXcsvPrices/Controls/SearchBox.type'
```

Rebased onto `RscExileXM8Edit`, which supplies `type = 2` and the XM8's
onSetFocus/onKillFocus handlers for keyboard capture.

### 7. Slides created visible

`ctrlCreate` does not honour the class's `show = false`, so all six app slides
appeared at once. Worse, being display-level, Exile's "slide it away" to
`x = -19*0.05` merely moved them elsewhere on the monitor rather than clipping
them - hence app content floating beside the tablet. Slides are now created
hidden and parked, and the shared teardown hides them on both grid-open and
grid-leave. That ordering is safe because
`ExileClient_gui_xm8_slide` runs the incoming onOpen, then the outgoing onClose,
and only then shows the incoming slide.

## Layout

`RscXcsvXM8AppButtonGrid` is a new base at `4.25*(0.04)` tall with ShortcutPos
and TextPos scaled by the same fractions, so icon and label scale WITH the
button. This has to live in config; resizing at runtime is precisely what broke
the labels. Four rows of 4.25 = 17 units, which is the space above the slide's
GO BACK button. App slots 10-13 are declared but carry neither icon nor name and
are skipped, so the 16 real apps close ranks instead of leaving four holes.

## Icons

Exile ships 14 XM8 icons and every one is already used by a stock app, so there
was nothing to reuse - and no PNG-to-PAA converter on this machine.

`E:\ArmaTools\paa.ps1` was written to close that: a PAA reader/writer with no
external dependencies, in the same spirit as `pbo.ps1`. Verified against the real
Exile icons - the parser reproduces `boom`, `territory` and `user` identically,
and encoder output is **exactly 22016 bytes** with **124 of the first 128 header
bytes byte-identical** to stock, the only differences being the image-specific
AVGC tag.

The decisive finding was that every Exile icon stores its mipmaps
**uncompressed** - the OFFS offsets reconcile exactly with raw DXT5 sizes. That
meant a DXT5 encoder was needed and an LZO compressor was not.

Comparing AVGC against stock also revealed the house authoring rule: stock reads
`F3 F3 F3`, i.e. RGB is near-white across the WHOLE texture and alpha alone
carries the glyph. Leaving the transparent region black makes mipmap filtering
bleed a dark halo into every edge. Ours read `FF FF FF` with alpha coverage
0x29-0x49, bracketing stock's 0x37.

`E:\ArmaTools\make-xm8-icons.ps1` draws all six and encodes them, so the art is
one command to revise.

## Bugs found in my own work, caught before shipping

- **Every outline rendered invisible.** The colour was held in `$W` and the pen
  width parameter was `$w`; PowerShell variable names are case-insensitive, so
  `New-Object Pen($W, $w)` became `Pen(9, 9)` and coerced the width into a
  Colour of `A=0` - a fully transparent pen. No exception, fills present, every
  stroke silently missing. Caught only by rendering a contact sheet and looking
  at it.
- **`[int]($i/3)` rounds in PowerShell**, it does not truncate, so the contact
  sheet dropped an icon. Third cast trap of the day after `0xFFFFFFFF` parsing
  as Int32 `-1` twice.

## An LZSS decompressor, written and then removed

To read the stock `extraApps_onOpen` from the client PBO, an LZSS decoder was
added to `pbo.ps1`. Three plausible dictionary variants each produced a
different wrong checksum - 24381, 34624, 28869 against a stored 31157 - and all
three produced output that read like plausible SQF for a few hundred bytes
before drifting.

It was removed rather than finished, because it was not needed: a vendored copy
of `ExileClient_gui_xm8_slide.sqf` was already on disk under
`E:\ExileRepo\Addons\ExAd`, and that is what revealed the `CfgXM8 >> controlID`
lookup that fixed the parenting. `pbo.ps1` refuses compressed entries again, with
the checksum discipline recorded in a comment for whoever picks it up.

Emitting garbage that looks like source is worse than emitting nothing.

## Verified in game

Operator screenshots confirm rendering for **Scoreboard** (real data, 4 players
ranked), **Standing** (three factions with bars), **Field Notes** (working left
nav and formatted body), **Trader Prices** (item list and detail pane) and
**Insurance** (policy state and buy button). All show GO BACK.

**Player Inspector** renders its frame and GO BACK but its content area was
empty. That was observed while slides were still bleeding over each other, so it
is not yet a trustworthy observation - unverified, not known-broken.

Server boots clean after every deploy: one mission start, `Server is up and
running`, no `No entry` errors, no texture load failures.
