# GUARD-STACK-001 - a stack supervisor, and an operator intent latch

Work ID: `GUARD-STACK-001`

Owning repo: `XCSV_GUARD`

Priority: P1 - the stack does not fully recover after a restart, and the worst
gap is silent

Gauntlet: G3

Date: 2026-08-11

Verdict: `PASS_BUILD_AND_TESTS` - **not runtime verified.** Nothing in this work
has been proven against a real restart cycle, because the server is live with a
player on it. See "What cannot be proven without a restart" at the end; that
section is the important part of this receipt.

## What was actually wrong

Three gaps, all evidenced before any code was written.

**MariaDB was not supervised at all.** GUARD reads the database but never
looked at the *service*. It has been found `Stopped` twice in two days despite
`StartType: Automatic`, which is the interesting detail: Windows restarts a
service that fails, but not one that was stopped deliberately, so "Automatic"
was never going to cover this. The consequence is the worst kind: extDB3
connects during world init, and if the database is not there the Arma server
exits **with no error line in the RPT**. The operator sees nothing start and has
nothing to read.

**The headless client did not reliably recover.** GUARD-HC-001 and -002 built
recovery that judges the HC on *join* evidence, correctly. But both arm a
one-shot judgement, and once its single replacement is spent, an HC that is
simply *absent* is never launched again. Server RPT
`arma3server_x64_2026-08-11_15-02-49.rpt` shows `Server is up and running`, 425
A3XAI hits and 17 FuMS hits, and zero headless-client connect lines. The AI runs
on the HC; no HC means no AI missions, which is the symptom that was reported.

**Only one HC was possible.** `hc_enabled` was the entire configuration surface.
The command line was baked into the binary.

Then the requirement grew, and it changed the shape of the answer: the stack
must keep itself up without anyone watching it - *except* during development,
when a deliberate stop must stay stopped.

## What was built

### A reconciler, not a boot sequence

`src/stack.rs` already documented the boot order in its module header. That
order is now expressed as data and a pure function rather than as a sequence
behind a button:

- `DesiredStack` - what should be true.
- `ObservedStack` - what is true, always probed, never inferred.
- `reconcile()` - one action, tiers strictly in order, no clock and no I/O.

It returns at the first tier with work, which is the whole ordering guarantee in
one testable place. The database is started, and *nothing else happens that
tick* - so the server is always launched against a database that has been
re-probed since, never against one GUARD merely asked to start.

`HoldServerForDatabase` is reachable only when database supervision is switched
off. It exists because starting the server into a stopped database is the
failure that leaves nothing to read, so GUARD declines and says why rather than
producing an undiagnosable outage.

Tier 3 will not touch the headless client until the server has passed
`Server is up and running` in the current RPT. A process that exists but never
reached mission start is not healthy; there is no mission to join.

### Operator intent, on disk

`StackIntent` (`xcsv_guard_intent.json`, beside the exe).

A component that is down looks identical whether it crashed or whether somebody
stopped it thirty seconds ago. No amount of probing distinguishes those, so
intent is recorded rather than guessed. STOP EVERYTHING latches maintenance;
START EVERYTHING clears it; a separate **Maintenance** toggle does either
without touching a process.

It is persisted because the case that matters is closing GUARD. A latch that
lived in memory would mean stopping the stack for the evening and reopening the
console tomorrow boots everything back up - exactly what was asked to be
prevented. It is read in `SupervisorCore::new`, before `tick_autostart` can run.

Default, and the default on a corrupt or missing file, is **supervising**. The
other choice silently disables the watchdog with nothing on screen to prompt a
second look.

Four paths could have started a server without going through any intent check,
and all four are now closed: `tick_autostart`, `tick_relaunch`,
`tick_restart_schedule` (which would have broadcast a warning to nobody, sent
`#shutdown` to nothing, then armed the relaunch timer), and the crash path in
`supervise()` (a process dying during maintenance is recorded and notified, but
not restarted). Each has a test naming the way it would have defeated the latch.

### Bounded recovery

`RecoveryBudget`: five attempts per component, delay doubling from 30s to a
10-minute cap, then **abandoned** - GUARD stops and says so loudly rather than
churning where nobody is reading. This estate has a 419 MB RPT on record from an
unbounded relaunch loop. A component observed healthy gets its budget back.

The watchdog starts the server by calling the existing `start_server()`, so
`block_start_on_bad_pbo` and the database gate still apply. A test asserts
`reconcile_start_server` never calls `.ctl.start(` directly; the watchdog must
not become a way around the integrity gate.

### Multiple headless clients

`hc_count` and `hc_instances` in config, resolved by `Config::hc_fleet()`.

With no explicit instances, **entry 0 is the base argument list byte for byte**.
That is asserted by a test, and it is the point: a config written before any of
this existed must produce the identical command line it produced yesterday.
Extra clients are derived by suffixing only the two things that cannot be
shared - `-name=` (the marker GUARD identifies processes by) and `-profiles=`
(Arma's write directory). Mods, port and connection details are copied, because
those genuinely are shared.

Two clients sharing a `-name=` are indistinguishable to every check GUARD makes,
so the duplicate is dropped rather than launched, and `hc_fleet_problems()`
reports it instead of it vanishing silently.

### GUARD-HC-002's guard: extended, not reversed

HC-002 refuses to judge an existing HC once the RPT has grown past
`RPT_TAIL_BYTES`, because the join line may have scrolled out of the window
`poll` reads. That decision stands. The window has **not** been widened and no
timer has been introduced.

Two things were added instead.

First, the asymmetry that HC-002 did not need to resolve: launching a client
that has **no process** requires no join evidence at all. It cannot be the
kill-a-healthy-HC mistake, because there is nothing to kill. So an absent client
is now launched unconditionally once the server is serving, which is the direct
fix for gap 2.

Second, evidence that survives GUARD restarting. `WatchLog`
(`xcsv_guard_rpt_watch.json`) records, per server RPT, the size of the file the
first time GUARD saw it and whether a join line was ever read in it. If a
previous GUARD started watching while the whole boot still fitted in the window,
it has read every byte since - so "no join line" is a fact about the server
rather than an artifact of where we looked, even though the file is now far too
big to re-read. If GUARD has no such record, it still declines. A test asserts
the case that must stay undecidable: a record that only began once the file was
already oversized proves nothing.

This is a record of GUARD's own observations with their provenance, not a cached
copy of the HC's state. It only ever answers "could GUARD have seen a join",
never "did the HC join" - the latter is still re-derived from the live log every
poll. It is classified in `state_model` on those terms.

### An answer to "why did it stop"

`StackJournal` (`xcsv_guard_stack.log`, beside the exe). Tab-separated, one line
per action: time, tier, action, reason. Every recovery, every latch transition,
every declined judgement, and the startup read of the intent file. The status
line holds one string that the next event overwrites and that dies with the
process; the journal is still there tomorrow, and still there after GUARD has
been restarted - which is when the question actually gets asked. A reason
containing newlines or tabs is flattened so an OS error message cannot forge an
entry. Rotates at 1 MB. Surfaced in a collapsible panel on the Overview.

### Saying what state things are in

`ComponentHealth`: HEALTHY / STARTING / UNEXPECTED DOWN / MAINTENANCE, per
component, derived each poll from the probed state and the desired state.

This is a direct response to today's misdiagnosis. GUARD launched the HC
correctly, ninety seconds after the server as designed, and with nothing on
screen saying so it was reported as "FuMS and A3XAI are not starting". Both were
loading fine. The raw chip said "starting"; nothing said whether that was
expected. Maintenance mode also gets an unmissable red banner: a watchdog that
has quietly stopped watching is worse than none, because the operator believes
they are covered.

## Configuration

New keys, all with defaults that reproduce today's behaviour exactly. An
existing `xcsv_guard.json` keeps working untouched - `#[serde(default)]` fills
absent keys, and a test deserializes a document containing none of them.

| key | default | effect |
|---|---|---|
| `db_service` | `MariaDB` | Windows service name. Was a literal in four places. |
| `supervise_database` | `true` | start it when found stopped |
| `hc_count` | `1` | headless clients wanted, capped at 8 |
| `hc_instances` | `[]` | explicit per-client parameters; empty means derive |

No new hard-coded paths. Every path in the new code comes from `Config` or from
`beside_exe`.

## Behaviour change worth stating plainly

Before this, whether GUARD brought the server back depended on
`autostart_server` and `auto_restart_on_crash`. Now, unless maintenance is
latched, GUARD will start the server whenever it is not running - through the
same gates, with the same backoff. That is what "the full stack is always up"
means, and the Maintenance switch is the off switch. It is a real change in
behaviour for a configuration that previously had autostart off, and it should
be watched for a cycle.

## Tests

**325 passed, 0 failed, 3 ignored.** 267 before this work, so 58 new. Run on
2026-08-11 with `cargo test` against the committed tree.

The ones worth naming, because they encode decisions rather than mechanics:

- `recovery_walks_the_tiers_in_dependency_order` - fix what the reconciler asks
  for, and it asks for the next tier. Never out of order, never two at once.
- `the_server_is_never_started_into_a_stopped_database`
- `a_server_that_never_reached_mission_start_blocks_the_headless_tier`
- `clients_are_replaced_only_on_a_trustworthy_not_joined_verdict` - `Undecidable`
  must never authorise killing a client.
- `a_log_past_the_window_with_no_record_stays_undecidable` - HC-002's guard,
  still standing.
- `a_log_watched_from_inside_the_window_can_be_judged_after_it_grows` - the
  honest extension of it.
- `maintenance_produces_no_action_no_matter_how_broken_the_stack_is`
- `no_timer_can_start_the_stack_while_maintenance_is_latched`
- `a_crash_during_maintenance_is_recorded_but_not_restarted`
- `intent_is_read_from_disk_in_the_constructor_before_anything_can_run`
- `the_first_client_is_the_existing_command_line_unchanged`
- `recovery_gives_up_after_the_cap_rather_than_hammering`
- `headless_presence_probing_is_throttled_off_the_poll_interval`

That last one is a fix for something introduced during this work: the first cut
of `hc_absent` scanned the whole process table once per client on the 2-second
poll, which is precisely the probe churn that measurably cost this server frame
rate on 2026-08-03. It is now cached for 30 seconds and invalidated whenever the
process table is known to have changed.

## INFERRED

- That MariaDB is being stopped by something rather than failing to start. This
  follows from `StartType: Automatic` plus two observed `Stopped` states, and
  from the shutdown ordering in
  `C:\Program Files\MariaDB 10.11\data\SOVRAN-1.err` for the 08-10 outage -
  clients of the database drop first, then the service stops. What is doing the
  stopping is still unknown, and this work does not find out; it only makes the
  consequence recoverable.
- That the absent HC on the 15:02:49 boot is explained by the one-shot
  recovery having already been spent. Consistent with the RPT and with how the
  code read, but not proven - there is no journal for that boot, because the
  journal did not exist until now.
- That `Server is up and running` in the incremental RPT scanner is a reliable
  proxy for "there is a mission to join". It is what the existing health scanner
  already uses, and the scanner resets on a new RPT, so it should not carry
  across boots. Not independently checked here.

## What cannot be proven without a restart cycle

None of the following was exercised, and none of it should be assumed to work
until it has been:

1. **MariaDB actually being started by GUARD.** `start_service` shells out to
   `Start-Service`. Whether that succeeds depends on elevation - the function
   already returns "could not start (needs elevation?)" for a reason, and there
   is a standing note in this estate that `\SOVRAN\` scheduled tasks needed
   elevation. **If GUARD is not elevated, tier 1 will fail every time, back off,
   and abandon after five attempts.** It will say so, in the journal and in a
   notification, which is a strict improvement on silence - but the recovery
   itself is unproven. This is the single most important thing to test.
2. **The ordering under a real cold start.** Database up, then server, then HC,
   with the server gate actually holding. Proven in unit tests against a fake
   `ObservedStack`; never run against real processes.
3. **The maintenance latch surviving a GUARD restart.** The file round-trip is
   tested. The end-to-end behaviour - stop the stack, close GUARD, reopen it,
   confirm nothing comes back - is not.
4. **Multiple headless clients.** `hc_count > 1` has never been run. The derived
   `-profiles=E:\arma3server\profiles_hc2_2` directory does not exist yet; Arma
   creates profile directories itself, but that has not been confirmed for this
   path. Nobody should set `hc_count` above 1 without watching the first attempt.
5. **The persisted watch log across a real GUARD restart.** Whether a restarted
   GUARD correctly reads its predecessor's record for the current RPT and
   reaches `NotJoined` where it previously declined.
6. **That the watchdog does not fight anything.** The four intent gates are
   asserted by source inspection, which proves the guard clause is present, not
   that the interaction is right. The GUARD-HC-001 receipt records the lesson
   directly: that bug was invisible to unit tests and to review, and only
   running the real scenario caught it. The same applies here.

## Recommended live test, when a restart is acceptable

In order, watching `xcsv_guard_stack.log` throughout:

1. Press Maintenance. Confirm the banner, confirm the countdown stops, close
   GUARD, reopen it, confirm nothing starts and the banner is still there.
2. Clear maintenance. Confirm the stack comes up in tier order.
3. Stop MariaDB by hand while the stack is up, and watch whether GUARD starts it
   again - this is test 1 above, and the elevation question is answered here.
4. Only then, a scheduled restart, watching for the HC join line.
